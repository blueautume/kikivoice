## 身份与权限

普通 Apple 业务身份、运维 Passkey 身份、LiveKit 媒体凭据分别使用，不相互代替。运维账户首次登录并设置姓名后仍默认零权限，第一位注册者也不自动获得权限；同名不合并身份。人工授权必须核对姓名和不可变的 `ops_` 编号。

运维权限分为：

| 权限 | 可访问范围 |
| --- | --- |
| `account` | 账号服务只读看板。 |
| `voice` | 语聊服务只读看板。 |
| `community` | 举报证据查询、警告、临时文字禁言、临时禁麦、语聊封禁、关闭违规房间、驳回及解除平台限制。 |

三个权限独立校验，两个看板权限都不能代替 `community`。客户端和公网 API 没有授予权限的入口；服务器 CLI 仍需精确姓名与账号编号。已为精确姓名“管理员”与编号 `ops_8cb320676bed4cdfbdbe21905051a5bb` 开通社区管理。线上只读核对确认该账号处于启用状态，权限为 `account`、`voice`、`community`，没有给其他真实账号扩权。

运维 App 向账号服务器的 `/admin/v2/services/voice/moderation/query`、`.../action` 发起请求。账号服务验证 `community` 后注入已认证的操作者编号，只签名转发固定语聊路径。语聊侧不复制运维账户、Passkey 或 ACL；仅在有期限的操作审计中保存不透明的操作者编号。

两个内部 moderation 路径只允许账号服务器源 IP，仍须校验独立 HMAC、精确方法与路径、原始请求体摘要、时间窗口和持久一次性 nonce。与原只读 dashboard 共用重放防线，不接受客户端自行提供的操作者、任意目标或目标 URL。旧管理口令不作为回退方式。

## 普通用户与房间管理

现有八麦、申请／邀请／审批、锁麦、房内禁麦／禁言、移出／解除房间禁入、房管任免、公告、结束房间与房主离场交接继续由服务器校验角色和目标。平台施加的限制不能通过房管操作、换麦、重新登录或旧媒体令牌绕过。

普通用户可在安全中心查看个人拉黑列表、最近处置通知、临时限制和本人举报状态。语聊封禁只限制语聊能力，不封禁 Apple 账号；业务会话仍可建立或续期，以访问安全状态、设置和退出／撤回／注销。被封禁者不能借此创建、发现或进入语聊房，旧 JWT 与信令重新授权同样受限制。

举报对象支持人、房间、消息。举报者须有服务器从 SFU 实际观察到的参与记录，仅获得入场令牌不构成已参与证据。消息所属房间、作者、正文和时间从服务器记录核实；只对仍在短时消息窗口内的消息生成按需证据快照，不接受客户端自造正文或冒认作者。没有消息证据时只能提交情况描述，不将其表述成已有音频证据。

同一用户的举报 UUID 在保留窗口内幂等；同 UUID 改内容返回冲突。每用户每分钟最多 3 条、滚动 24 小时最多 20 条，日总量限制跨进程重启生效。本人最多查看最近 100 条未过期记录。

个人拉黑的边界是：服务器隐藏本人读取到的对应用户消息和其编辑的公告；官方客户端先读取拉黑状态，再决定音频订阅，并停止接收被拉黑人音频。解除拉黑后可重新订阅。**公开房间仍可能共同在场，双方在线状态与成员列表不被隔离，不能将个人拉黑当成双向隐身或房间禁入。**

## 社区处理与实际媒体状态

处置目标来自服务器核实的举报，不接受管理员客户端任意替换目标账号。所有处置要求明确理由，并使用操作 UUID 防止超时重试重复执行。临时文字禁言、禁麦与语聊封禁的时长为 60 秒至 30 天；首版没有永久封禁标记。

- 警告向被处理用户发送社区提醒。处理消息举报的警告、禁言或封禁同时移除该条房间消息，原证据按保留期限单独保存。
- 临时文字禁言禁止对应语聊文字发布；临时禁麦禁止上麦及音频发布。房间状态与新令牌反映当前平台限制，房主不能取消平台限制。
- 语聊封禁先持久化，关闭该用户主持的房间，并移除其余语聊入场；Apple 登录和账号本体保持独立。
- 关闭违规房间停止其入场与现有信令。解除用户限制不会重新打开已经关闭的房间，也不会自动取消房主单独设置的房内禁言／禁麦。
- 驳回关闭举报处理状态，不自动撤销此前其他有效处置；解除平台限制使用独立的 `restore_user`。

媒体处置不能只更新业务表。服务端同步 LiveKit 发布权限、停止已有音轨，必要时关闭信令并尝试移除媒体。确认失败的任务持久化重试，管理端的 `mediaCleanupPending` 表示尚待媒体确认，不能显示成已完整清退。

待处理队列按最早举报优先，每批最多 50 条，处理后下一批进入；已处理及全部记录查询显示最近一批。有效制裁另有 `activeRestrictions` 列表，只保留目标账号编号、来源举报不透明编号和限制时间，不延长已到期的证据。即使原举报证据已删除，管理员仍可从该列表解除尚有效的限制。列表上限为 5000 项，响应显式提供上限及截断标记。

基础内容过滤作用于房名、分类、房内文字和公告，规整全角、大小写、空格和零宽格式字符后匹配配置短语。可用 `SAFETY_TERMS_PATH` 指定 `{"blockedTerms":["短语"]}` 的 UTF-8 JSON；最多 2000 条，每条 2–80 字符，配置错误拒绝启动。未配置时只有有限默认短语。**这是基础文字过滤，需要人工举报配合，没有实时语音识别、音频内容审核或录音取证。**

## 数据保留、撤回与跨服务顺序

| 数据 | 当前规则 |
| --- | --- |
| 举报、情况描述、按需房名／消息证据 | 最长 30 天，到期删除，未处理举报也不无限延期。 |
| 社区通知 | 最长 30 天，安全中心最多返回最近 50 条；首版无服务端已读状态。 |
| SFU 实际参与观察记录 | 最长 30 天，用于核实曾参与的房间。 |
| 可关联账号的活动记录 | 35 个上海自然日，包含当天。 |
| 最小操作审计、操作幂等回执 | 最长 90 天。 |
| 平台临时限制 | 按实际有效期保留，最长 30 天；解除或到期后同步清理。证据到期不提前解除较晚施加的限制。 |
| 每日数据备份 | 新备份校验成功后轮转超过 7 天的受管副本；故障期间保留此前成功副本。 |

注销或撤回清理双向拉黑关系、关联举报与证据、通知、观察记录和活动标识；操作审计清除自由文本理由和目标业务 ID，仅保留有期限的不透明回执。有效语聊限制不会因撤回协议而被绕过，正式注销完成后清理限制。此前已收到的文字、设备上的旧展示及历史备份无法承诺物理即时擦除。

跨服务撤回使用账号服务 `legal_consent_events.event_id` 的单调事件顺序：签名交换包含 `consentEpoch` 和 `lastWithdrawalEpoch`，撤回 outbox 携带 `reason=withdrawal` 与对应 `consentEpoch`。语聊在接受新的同意版本前，先清理此前尚未送达的撤回及旧授权；之后迟到的旧事件只撤销旧来源，不会撤回新同意或误删新产生的安全数据。同秒内的撤回、重新同意也按事件编号区分。普通退出登录仅撤销会话，不清除用户拉黑设置。

## 运营指标口径

两台服务器看板继续标明来源，账号数据不混入语聊服务器。新增活跃与回访按成功业务认证的稳定账号编号去重，不表示已识别自然人；历史无记录不推算，均注明统计起点。

语聊在线账号按新鲜 SFU 观察与有效入场成员交集全服去重，采样缺失则为未知；准入占位、SFU 原始连接数和活跃账号是不同口径。房间停留是约 5 秒采样估计，仅累计相邻间隔不超过 15 秒的观察，不补算进程重启或采样中断。上麦是授权进入麦位次数，不是实际持续发声时长。举报指标显示当前保留数据范围内的提交与待处理情况。

看板增加固定路径备份状态：缺收据显示未知，最后成功超过 36 小时、恢复副本校验失败或状态无效时告警；不向 App 暴露私有文件路径、配置或原始错误日志。告警属于看板展示，本轮没有新增向外部联系人发送通知。

## 每日备份与恢复边界

维护脚本位于 [`experiments/livekit/infra/maintenance`](../experiments/livekit/infra/maintenance/)：`data_backup.py` 创建并校验副本，`install_maintenance.py` 安装固定主机的 systemd 服务与 timer，`test_data_backup.py` 验证维护行为。

| 项目 | 账号服务器 | 语聊服务器 |
| --- | --- | --- |
| 定时器 | `kiki-account-data-backup.timer` | `kiki-voice-data-backup.timer` |
| 每日基准时间 | 03:30，Asia/Shanghai | 03:40，Asia/Shanghai |
| 随机延后 | 0–10 分钟 | 0–10 分钟 |
| 执行用户 | `kikitalk` | `livekit-lab` |
| 在线数据目录 | `/var/lib/kikitalk` | `/var/lib/kiki-livekit-lab` |
| 备份目录 | `/var/lib/kikitalk-backups` | `/var/lib/kiki-livekit-backups` |
| 状态收据 | `/var/lib/kikitalk/backup-status.json` | `/var/lib/kiki-livekit-lab/backup-status.json` |

timer 使用 `Persistent=true`；任务错过时会补调度，不保证绝对准点。固定服务用户运行维护，目录 `0700`、数据库／副本／收据 `0600`，避免 root 写入 SQLite WAL/SHM 造成属主竞态。账号副本含一致性 SQLite 和数据库实际引用的头像；语聊副本含语聊 SQLite。脚本不复制 PEM、Apple 私钥或服务器环境凭据。

备份通过 SQLite 一致性接口生成，生成清单与 SHA256，检查完整性和外键，再复制到临时隔离目录检查恢复副本、表结构及账号头像引用；不启动恢复副本的 API，不联系 Apple／LiveKit，也不覆盖在线数据库。只有新备份及副本校验成功后才删除超过 7 天的受管副本；失败保留上次成功与其时间，收据记录失败，不能冒充新成功。连续故障时副本可能超过 7 天，须处理告警，不能将保留旧副本当成定时成功。

这些副本位于同一台主机，属于本机数据保护，**尚无异地副本或整机故障容灾**。副本校验通过也不等同完成真实业务恢复演练。

正式恢复必须另行安排维护窗口：先停止对应 API，核对快照归属、代码／数据库版本、清单与权限，并保留待替换数据副本；核对账号侧 `voice_revocation_outbox`、撤回／删除事件和语聊侧隐私 epoch、制裁及 `media_cleanup` 等待确认记录，防止旧快照重新开放已撤销的权限或恢复已删除资料。必要的清理与同步完成后再恢复服务并验收。每日脚本没有自动执行这些在线替换步骤。

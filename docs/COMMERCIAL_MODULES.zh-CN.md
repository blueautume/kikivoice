# KikiTalk 商用模块分级清单

规划日期：**2026-10-16**。本文是面向中国大陆市场、首发包含礼物/充值或会员的实施规划，**不代表这些功能已经完成、腾讯云服务已经开通，或产品已经具备上线资格**。本次只审查代码与公开资料，没有更改程序、部署或云配置。

清单共 **104 个模块**：🔴 **P0 核心 44 项**、🟠 **P1 必要 30 项**、🟡 **P2 重要 20 项**、🔵 **P3 演进 10 项**。颜色同时附带文字级别，便于打印和无障碍阅读。

## 如何使用分级

- **🔴 P0 核心**：相应首发业务公开前必须完成的功能与保护措施，包括付费资金安全、基础内容安全、账户安全、管理权限、异地备份和故障发现。
- **🟠 P1 必要**：完整产品通常需要的服务与管理能力，优先在首发前后补齐；若已经承诺在首发公开，相关基础功能、风控和可靠性要求相应升为 P0。
- **🟡 P2 重要**：改善运营效率、增长、规模和体验，在安全可用的基础上按实际数据投入。
- **🔵 P3 演进**：由规模、组织或战略需要触发的长期建设，不因“商用”就默认引入。
- **条件优先于默认分组**：公开私聊就必须同时完成拉黑、举报、审核和骚扰控制；公开直播就必须完成直播治理；开放主播提现或公会分成，相应资金、资质、税务、反作弊和申诉模块升为 P0。不开放的业务应在客户端、接口、管理台和远程配置中保持关闭。
- 各模块是可分工实施的能力边界，**不等于必须拆成 104 个微服务**。建议先采用模块化后端、独立异步 Worker 和清晰的数据归属，按瓶颈逐步拆分。

现状标签只使用三种：**已有基础**表示仓库中已看到部分相关实现，不等于达到商用验收；**未接入**表示当前正式产品未看到该能力的完整实现；**待核验**表示需要控制台、合同、资质、真机、容量测试或实际运维证据才能确认。

## 当前基础与架构边界

已审查的正式产品是 **iOS 原生客户端 + 自有 FastAPI/SQLite 服务 + 腾讯实时互动服务**。iOS 已具备 ID/设备密钥登录、首次昵称、相册头像、我的资料、收藏/历史、语聊/直播和八麦房间、应用内最小化等基础。服务器已有会话、UserSig 签发、资料、房间登记、收藏、历史、头像验证、本机一致性备份、健康检查和 systemd 运行配置。

这些基础不能推出“完整商用已具备”：当前未见 Android/鸿蒙正式产品工程、完整私聊/Push、支付账本、举报封禁申诉、业务管理台与自动异地备份的完整实现。云端实际套餐、控制台审核配置、配额、资质、商户、域名及外部监控仍待核验。未对当前服务器做容量基准测试，因此本文不承诺具体在线人数或 QPS。

腾讯服务承担实时音视频、实时房间/麦位/成员与房间消息。**自有数据库应掌握业务账号、付费订单、账本、会员权益、举报证据索引、处罚、运营配置和管理审计的权威记录**。使用腾讯 RTC 不意味着已使用腾讯 COS、云数据库、Push、云端审核或云录制；这些都需分别选型、开通、授权与预算。

现有单机 API 直接提供 HTTPS，SQLite 和头像在本机；直接增加 API 实例会遇到共享存储、数据库写入与进程内限流问题。应先完成事务数据库/对象存储与状态外置，按实际 SLA 采用负载均衡及双实例，再据压测决定弹性扩容。媒体流走腾讯云，业务 API、上传、审核回调、资金回调、房间目录和数据库仍会独立成为瓶颈。

## 实施先后与验收原则

1. **收敛首发范围**：明确三个客户端是否同时首发、先开语聊还是也开视频、礼物和会员哪些开放；未纳入的能力真实关闭。
2. **补商用底座**：账户恢复、域名/TLS、事务数据模型、管理权限、审计、异地备份、监控、内容治理和举报处罚闭环。
3. **做完整付费闭环**：商品→支付→服务端验单→幂等订单→账本→钱包/会员/礼物→退款冲正→对账与人工补偿；沙盒和生产完全分开。
4. **完成多端互通**：共享 API/业务规则，各端原生媒体与系统能力单独适配；原生鸿蒙先做八麦/房管/后台音频/支付真机 PoC。
5. **以故障场景验收**：重复回调、乱序、支付后断网、加币前进程崩溃、退款后重登、封号后旧 UserSig、主播掉线、备份恢复、主机失效都必须有结果证据。
6. **再按数据扩展**：私聊/Push 完整体验、运营效率、增长、推荐、弹性和高级平台建设按实际经营投入；任何已经对外开放的能力，其安全和可靠性保护必须同步到位。

每个模块落地时至少补充：**负责人、依赖、具体 API/表、云产品与成本、验收场景、告警、回滚/补偿和运营手册**。表中的“已有基础”需逐项转为有证据的验收结果，不能直接标记完成。

## 关键官方参考

以下是公开能力参考，不代表当前账号已开通。产品能力、套餐、审核规则和商店条款应在实施与上线时重新核对。

- [腾讯 Live/TUILiveKit 组件与平台表](https://intl.cloud.tencent.com/zh/document/product/647/60034)：iOS/Android 有成熟接入；完整鸿蒙 UI 能力不能仅由 TRTC 底层支持推导。
- [TRTC 原生 HarmonyOS 接入](https://cloud.tencent.com/document/product/647/130532)、[IM HarmonyOS API](https://cloud.tencent.com/document/product/269/103559)、[AtomicXCore/RoomEngine 发布日志](https://cloud.tencent.com/document/product/269/125816)：原生鸿蒙媒体、IM 与部分底层能力已有公开资料，仍需验证当前产品所需接口和版本。
- [腾讯 Push 各通道与结果回调](https://cloud.tencent.com/document/product/269/102568)、[HarmonyOS Push 接入](https://cloud.tencent.com/document/product/269/137329)：APNs、各 Android 厂商、鸿蒙分别配置；设备送达和业务已读是不同状态。
- [IM 失效账号登录态](https://cloud.tencent.com/document/product/269/3853)、[IM 全局禁言](https://cloud.tencent.com/document/product/269/4230)、[Live 成员管理](https://cloud.tencent.com/document/product/647/110041)：旧 UserSig 失效后，新签发仍可登录；业务封号必须停止签发并联动各实时链路。
- [腾讯回调安全、超时与重试](https://cloud.tencent.com/document/product/269/1522)：验签、防重放、去重和超时策略需单独落实，不能把慢速审核放在同步前置回调里。
- [IM 消息存储](https://cloud.tencent.com/document/product/269/3571)、[IM 群组与直播群历史差异](https://cloud.tencent.com.cn/document/product/269/1502)：不能默认永久保存消息，举报证据需要独立受控固化。
- [腾讯礼物系统](https://intl.cloud.tencent.com/zh/document/product/647/69849)：礼物目录、展示及云端接口可复用；自有收款、钱包、账本、退款和结算仍需完整建设。
- [Apple App Store Server API](https://developer.apple.com/documentation/appstoreserverapi)、[App Store Server Notifications](https://developer.apple.com/documentation/appstoreservernotifications)：服务端交易/订阅查询、签名信息、退款和通知用于构建验单与补偿闭环。
- [华为 IAP Kit](https://developer.huawei.com/consumer/cn/sdk/iap-kit/)：原生鸿蒙支付需按实际发行渠道与商品类型完成客户端和服务端接入。

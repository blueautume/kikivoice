## 1. 结论与资料导航

当前项目已具备真实语聊产品的 iOS 起点；距离可持续收费运营，还需要建设**身份与资金安全、内容治理、业务管理台、可靠数据与运维、多端一致性**五条主线。不能通过增加几台服务器、打开腾讯礼物按钮来补齐这些能力。

建议采用 **三端原生客户端 + 按领域划分的模块化业务后端 + 独立异步 Worker + 托管关系数据库 + Redis + 对象存储 + 腾讯实时互动服务**。初期无需拆成大量微服务；资金、处罚和账户的权威数据由自有后端掌握。

## 3. 当前系统的真实边界

| 层面 | 已核实事实 | 商业化缺口 |
| --- | --- | --- |
| iOS | SwiftUI 产品页面、UIKit 房间、ID/设备密钥登录、首次昵称、相册头像、我的资料、收藏/历史、真实八麦房、应用内悬浮球 | 找回/换机、多端身份、私聊与通知、支付、完整隐私与治理入口 |
| Android / 鸿蒙 | 当前仓库未发现正式产品端工程 | 分别建立产品工程和验收矩阵，鸿蒙先做房间能力 PoC |
| 实时互动 | AtomicXCore / RTCRoomEngine 4.3.10、TXLiteAVSDK Professional 13.4.21067、本地 TUILiveKit / AtomicX | 房间与媒体控制深度依赖腾讯；全站治理、资金和运营仍需自建 |
| 业务 API | FastAPI；会话、UserSig、资料、房间登记、收藏、历史；基础限流与图片格式校验 | 管理员、举报、处罚、审核、通知设备、支付账本和云回调尚未完整接入 |
| 数据 | SQLite WAL；头像在业务机磁盘 | 单写者、文件与服务耦合、缺少生产数据库迁移和 HA 方案 |
| 部署 | 单个 Uvicorn 进程直接监听 443；systemd 自动启动与重启 | 缺少入口负载均衡、双副本、共享状态、完整外部监控与发布体系 |
| 备份 | 同机发现手动历史快照；新版包含数据库与头像 | 未发现操作系统定时业务备份；未核验云盘快照；缺少已验证异地恢复证据 |
| 通知 | 当前是用户资料中的布尔偏好 | 不等于站内通知、APNs/厂商 Push 或离线私聊已实现 |

2026-10-16 服务器只读采样：**2 vCPU、约 1.9 GiB 内存、50 GB 根磁盘已用约 5.8 GB**；业务进程约 42–60 MiB，采样时负载低、服务正常。数据库约 68 KiB，只有少量记录。**这些是空闲小样本，不能推导在线用户上限或商业峰值容量**。

部署参数 `--limit-concurrency 100` 是 HTTP 并发门槛，不代表 100 个在线用户或 100 个麦位。音视频流由腾讯云承担，不会全部经过这台业务服务器。

主要代码证据：`backend/app/main.py:125`（表）、`:256`（进程内限流）、`:384`（ID 登录与写锁）、`:473`（头像写锁）、`:527`（房间查询）、`backend/deploy/kikitalk.service:14`（部署）、`backend/deploy/backup.sh:20`（备份写锁）。

## 4. 推荐生产架构与职责

### 4.1 客户端

- iOS 延续 Swift / SwiftUI / UIKit；Android 使用 Kotlin 原生工程；原生 HarmonyOS 使用 ArkTS / ArkUI。共享业务协议、设计规范、错误码与测试用例，不承诺共享全部 UI/媒体代码。
- 所有端通过自有 API 获取账号、处罚状态、房间准入、订单和权益；SDK 的 UserSig 不充当业务 Session。
- 媒体直连腾讯实时云；消息走选定 IM；客户端不能决定商品价格、最终余额、封禁状态和开播资格。
- 每端建立 `AccountService / RoomService / ChatService / NotificationService / PurchaseService` 等适配边界，产品 UI 不直接依赖供应商类型。当前 iOS 房间 Store 深度耦合需要渐进封装，不能声称换接口即可零成本切换 RTC。

### 4.2 服务端与数据归属

| 领域 | 权威数据与职责 | 关键边界 |
| --- | --- | --- |
| 身份/用户 | 自有 UID、认证绑定、设备、Session、资料、同意记录、关系与隐私 | UID、展示 ID、腾讯 UserID 分离；提供受限账号申诉/退款入口 |
| 房间 | 业务房间 ID、每次开播 Session、资格、访问策略、运营目录 | 媒体连接与座位由选定云能力执行；回调和定期对账核实状态 |
| 资金/权益 | 商品版本、订单、渠道交易、追加账本、余额、会员、退款、对账 | 事务与幂等确认后发货；不依赖客户端回报或礼物动画计数 |
| 治理 | 审核、举报案件、证据索引、处罚范围、执行结果、申诉 | 同时控制业务 API、IM、RTC、上传、开播和付费；保留必要救济渠道 |
| 通知 | 业务通知主记录、未读、偏好、设备 Token、投递记录 | Push 是提醒，不是业务事实和用户已读证明 |
| 运营/管理 | 内容配置、主播准入、活动、客服、财务工作台、管理审计 | 管理 API 与用户 API 隔离；敏感动作有理由、审批、日志 |
| 异步任务 | 回调 Inbox、事务 Outbox、队列、重试、死信、补偿 | 允许至少一次投递，消费者必须幂等；不假定天然“恰好一次” |

生产入口建议：正式域名、公开 CA TLS、WAF/基础抗攻击、负载均衡。API 至少双副本的方案服务于可用性，未必首先需要自动扩容。数据库和 Redis 位于私网；管理入口受 MFA、最小权限和受限网络保护。

事务数据库选定一套托管 PostgreSQL 或 MySQL；Redis 用于短期缓存、分布式限流等，不作唯一资金账本；对象存储分公开媒体、私有证据、录制与隔离备份；队列和 Worker 处理审核、Push、回调、对账和处罚执行。初期可用 CVM/容器与托管服务完成，不强制 Kubernetes。

## 5. 腾讯云用了什么，哪些绑定较深

| 能力 | 当前是否使用 | 绑定程度与替换成本 |
| --- | --- | --- |
| TRTC / LiteAV 实时音视频 | 已使用 | 高；各端采集、发布订阅、设备、弱网、质量事件和服务端控制均需适配与重测 |
| RoomEngine / AtomicXCore / TUILiveKit | 已使用 | 高；当前麦位、成员、房间 Store、UI 与生命周期直接相关 |
| 腾讯 IM 的房间消息/资料能力 | 已随实时栈使用 | 中高；正式私聊产品链路仍未完整接入；消息漫游、群型与历史按当前产品/版本确认 |
| SDKAppID / UserSig | 已使用，后端签发 | 腾讯专有鉴权；自身会话、账号、处罚和订单不得依赖它作为权威身份 |
| 云数据库 / Redis / COS / CDN | 当前业务代码未接入 | 可选腾讯产品，也可换其他厂商；标准 SQL、对象 Key 与自有元数据降低迁移成本 |
| Push / 内容审核 / 云录制 | 未见完整产品接入，控制台未核验 | 与 RTC 独立选型、授权、计费和配额；SDK 能运行不代表已购买这些服务 |
| 礼物展示/云接口 | SDK 有相关能力，当前产品入口关闭 | 展示和云交互可复用；真实收款、账本、退款、对账和收益结算不能据此假定已具备 |

没有任何能力在技术上永远无法迁移，但实时栈和历史消息迁移成本明显较高。建议先隔离接口和 ID 映射，保证数据可导出；暂不实现双 RTC 同时运行。不得假定同一房间中的两个供应商媒体可以自动互通。

原生鸿蒙的 TRTC 和 IM SDK 已有官方能力；但当前 Live 组件平台表未列出完整 HarmonyOS UI。应验证八麦同步、房管、消息、后台音频、支付与跨端互通后再承诺排期。[TRTC 鸿蒙接入](https://cloud.tencent.com/document/product/647/130532)、[Live 平台与组件](https://cloud.tencent.com/document/product/647/105438)。

## 6. 首发付费闭环

推荐顺序：**服务器商品与价格 → 订单 → 渠道购买 → 服务端验证 → 幂等交易入库 → 账本/权益原子提交 → Outbox → 礼物展示或会员到账 → 退款与日终对账**。

- iOS 大陆数字会员、虚拟币/礼物按适用 App Store IAP 规则设计；Android 按具体发行渠道核验支付路径；原生鸿蒙接独立 IAP Kit。支付、Push、账户统一不意味着三端必须用同一个支付 SDK。[Apple 支付规则](https://developer.apple.com/app-store/review/guidelines/#in-app-purchase)、[华为 IAP Kit](https://developer.huawei.com/consumer/cn/sdk/iap-kit)。
- 服务端验证环境、应用、商品、金额/币种、渠道交易 ID 和账号归属；使用最小货币单位整数。关键事务唯一键与锁/版本校验防重复入账、并发超扣和跨账号认领。
- 礼物动画/云接口失败时按明确规则重投或补偿；不要把动画成功当扣款依据。订单、账本、礼物业务单分别建模并关联，避免一个“余额字段”承担所有职责。
- 冲正、退款和调账追加新流水；赠币、付费币、可结算收益与实际人民币往来分清。封号不抹余额，不阻断依法或依约应提供的退款、申诉与注销。
- 会员的续费、取消、到期、恢复购买、退款撤权、宽限状态都由服务端权益中心处理。三端权益共享及各渠道消费余额策略须符合渠道规则，不作未经核验的通兑承诺。
- 若不开放提现，关闭收益提现全链路；若开放，主播准入、合同、风控冻结、结算、税务、打款与退单追偿都为条件 P0。不要直接设计可自由转账、兑换或提现的用户充值钱包。

2026 年直播打赏规则对限额、提醒、公开消费统计、排名和异常打赏等提出要求；需要落实到商品、风控、运营配置和客服流程。未成年规则应按现行分龄要求核验；产品可首期采取更严格的成人与打赏策略。[网信办打赏规范通知](https://www.cac.gov.cn/2026-04/13/c_1777815804150225.htm)。

## 7. 举报、封号与审核不能仅做页面

举报链路：**就近举报入口 → 服务端固化对象与上下文 → 案件队列/紧急分流 → 机审与人工复核 → 处罚决定 → 多系统执行 → 生效核验 → 反馈与申诉**。

处罚按范围建模：禁私聊、禁房间文字、禁麦、禁开播、房间封禁、限制充值/赠礼/提现、账号限制等。执行器记录每个系统的任务、结果、重试与告警，不能仅写 `banned=true`。

腾讯 IM 的历史 UserSig 失效后，重新签发仍可登录，所以必须同时禁止业务续签；IM 踢出或文字禁言也不证明 RTC 媒体已经被切断。房间权限票据是否适配当前 Live 封装需先验证，不能直接打开高级权限开关导致旧端全部进房失败。[IM 登录态失效](https://cloud.tencent.com/document/product/269/3853)、[TRTC 权限控制](https://intl.cloud.tencent.com/zh/document/product/647/35157?lang=zh)。

实时审核与证据需保留发言人 UID、房间会话、麦位/音轨和时间对应关系；混音片段未必足以定位发言者。审核回调、消息回调、客户端举报证据的真实性等级要区分。录制、审核、检索、人工查看分别控制权限和保存期限，不默认永久录下全部私聊与房间。

具体资质由经营主体、内容类型、是否网络表演/经纪等共同决定；APP 备案、实名、隐私、举报和商店 UGC 要求纳入上线准入。不因“音频”就排除直播治理，也不因有“直播”就一律套用直播电商规则。[APP 管理规定](https://www.cac.gov.cn/2022-06/14/c_1656821626455324.htm)、[Apple UGC 要求](https://developer.apple.com/app-store/review/guidelines/#user-generated-content)。

## 8. 我的、通知、私聊和 Push

“我”应包含个人资料、账号绑定/设备、隐私与黑名单、通知偏好、订单账单、会员、余额、帮助客服、举报/申诉进度、开播记录、退出与注销。主播收益仅在业务真正开通后显示。

私聊需要会话列表、发送状态、失败重试、历史策略、多端未读、陌生人请求、免打扰、拉黑和消息举报。可先使用腾讯 IM 成熟能力，业务准入、反骚扰和处罚仍由自有策略执行。不同云产品的房间历史与私聊历史能力不可互相推导。

业务通知先持久化，再异步 Push；支付和处罚状态以业务数据库为准。APNs、Android 国内厂商、鸿蒙通道分别登记环境和设备 Token；退出换号注销解除绑定，锁屏内容尊重隐私设置。深链回到具体订单/房间时重新鉴权；禁房、已结束、已退款或旧版本均有兜底。Push 不保证送达，回执不等于已读；营销消息有独立同意、频控和退订。[腾讯 Push 通道回调](https://cloud.tencent.com/document/product/269/102568)。

## 9. 管理台、运营与运维分开设计

| 工作台 | 必须具备的业务能力 | 不能混同的权限 |
| --- | --- | --- |
| 平台管理 | 用户/房间查询、资格、处罚、申诉、配置开关、审计 | 不能让所有管理员拥有数据库与财务权限 |
| 内容安全 | 待审队列、巡房、举报证据、紧急关房、复核、质检 | 证据和私聊访问按案件授权，有访问记录 |
| 客服 | 找回、付费掉单、退款申请、未成年人退款、投诉、SLA | 客服受理不等于可以改余额或审批自己的退款 |
| 运营 | 分类推荐、Banner/CMS、公告、主播准入、活动、用户分群 | 批量 Push、发币、商品调价必须审批和留档 |
| 财务 | 订单/账本、日终对账、差错、退款审批、收入与结算 | 调账使用追加流水与双人审批，不能直接改库 |
| 运维 | 发布回滚、监控、备份恢复、密钥、容量、供应商配额、事故 | 云 root、生产数据库、审核后台分权并定期回收 |

管理前端可选 TypeScript + React/Vue，基于团队能力选一套；后台服务复用同一领域逻辑，通过独立管理 API 和权限策略访问。服务器面板、腾讯云控制台均不能替代业务管理台。

## 10. 存储、备份与安全基线

- 关系库：账户、订单/账本、权益、案件/处罚、通知元数据；敏感身份字段加密隔离。
- 对象存储：公开头像/封面、私有举报证据、受限录制、运营素材分别设访问策略；审核前放隔离区，采用短期授权上传和服务器复检。
- 日志与审计：请求、事件、管理动作、支付/处罚执行有 Trace ID；不记录 Token、密钥、身份证原文和无必要私聊正文。
- 备份：自动一致性备份 + 数据库日志/PITR + 对象版本/独立副本；独立权限、加密、异地或隔离账号保存。主从复制和同机快照不等于独立备份。[SQLite WAL 边界](https://sqlite.org/wal.html)、[COS 跨桶复制](https://intl.cloud.tencent.com/document/product/436/19237)。
- 恢复：先在隔离环境演练，验证账本平衡、对象完整性、处罚状态及删除清单，再决定切换；恢复后补拉支付/RTC/IM 事件，不让已注销用户因旧备份复活。
- 初步建议业务数据备份目标 RPO ≤15 分钟、恢复目标 RTO ≤60 分钟；资金已确认交易另设更严格的持久化目标。这些是待预算和演练验证的目标，不是当前系统已达到的承诺。
- 正式域名与公开 CA 解决换证/换 IP 发版耦合；如保留 Pin，设计备份公钥与重叠轮换。生产/测试账号、商户、SDKAppID 和密钥隔离，轮换开发阶段共享过的凭据。

## 11. 性能与弹性扩容结论

当前存在明确的**架构瓶颈风险**，但没有证据证明已出现高负载性能故障：

1. SQLite WAL 仍只有一个写者；登录在写锁内计算 PBKDF2，头像 fsync 与备份复制也占写锁。增加 API Worker 不能消除单写瓶颈。
2. 房间列表缺少对应排序复合索引，已观察到全表扫描和临时排序；少量数据时不代表未来没有问题。
3. 头像由 Python 服务发送并禁缓存；并发上传的解码内存不能只按 2 MiB 压缩文件估算。迁对象存储、上传限并发及审核隔离后再扩 API。
4. 本地文件、SQLite、进程内限流都没有为多副本共享设计；直接克隆机器会造成数据和规则分叉。
5. RTC/IM、审核、短信、支付、Push 的云配额、吞吐和账单是独立瓶颈，业务机扩容不会自动提高供应商配额。

正确顺序：**正式入口与观测 → 状态外置/托管数据库/对象存储 → 双实例与可靠 Worker → 压测 → API/Worker 分别弹性 → 数据库与云配额扩展**。

弹性策略必须同时考虑 CPU、请求 p95/p99、5xx/503、连接池与锁等待、队列最老任务、审核和支付回调延迟。设置最少/最多实例、冷启动预热、扩容冷却、缩容排空、数据库连接总预算与费用上限。账本和数据库不随 API 副本自动扩写。

容量以真实场景测试：登录风暴、房间发现、进退房、多人同时送礼、重复支付通知、头像上传、审核回调积压、云端故障、DB 切换和持续运行。未经测试不承诺“支持万人”；媒体 CCU、业务 QPS、活跃账户、房间数与并发上传要分别核算。

## 12. 分期交付与上线验收

| 阶段 | 交付重点 | 退出条件 |
| --- | --- | --- |
| A：范围与技术验证 | 三端范围、付费种类/提现开关、主体资质、云套餐；鸿蒙房间/后台/Push/支付 PoC | 业务边界明确，供应商能力与渠道路径有证据 |
| B：商用底座 | 统一身份与恢复、域名、数据迁移、管理权限、审核举报封禁、备份监控 | 能封禁现有连接、受理申诉、完成恢复演练；无高危权限绕过 |
| C：资金闭环 | SKU、订单、验单、账本、礼物/会员、退款对账、财务控制 | 重复/乱序/掉单/并发超扣/退单/崩溃恢复测试通过；账本与渠道可核对 |
| D：多端与产品完整性 | 三端房间互通、我的、私聊、通知 Push、客服运营、真机质量 | 三端共用账号/权益/处罚，后台音频与弱网、升级与恢复通过 |
| E：受控收费上线 | 小流量灰度、审核客服排班、告警值班、故障演练、渠道审核 | 实测容量留有余量；问题可回滚/补偿；关键告警有人处理 |
| F：规模运营 | 活动、推荐、主播经营、分析、弹性、精细风控 | 以留存、服务质量、违规率、付费与单位成本决定下一阶段 |

上述阶段不是工期或费用承诺。项目应配置移动端、后端、后台前端、测试、运维、安全/合规、审核客服、运营与财务负责人；小团队可兼任，资金审批与执行等不相容职责不能由同一人无约束完成。

最终上线验收至少包括：未验证身份找回、旧 UserSig 封禁、坏客户端绕过审核、主播断网与跨端重连、Push 换号串发、支付成功未到账、重复回调双扣、退款后权益未撤、举报证据失效、管理员越权、数据库恢复及供应商故障降级。不能用“页面能点、演示成功”替代这些验收。

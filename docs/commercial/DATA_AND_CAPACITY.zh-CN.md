# KikiTalk 商用数据、容量与迁移方案

> **归档规划（2026-10-16；2026-10-22 标注）：** 本文保留当时的预算、腾讯方案与功能起点，不是当前架构、依赖或已交付功能清单。当前主线为 Apple 登录、自建 LiveKit、账号/社交及独立运维 App；已移除旧腾讯 iOS 组件、示例和实验客户端。当前入口见[项目接手指南](../PROJECT_HANDOVER.zh-CN.md)与[架构说明](../ARCHITECTURE.zh-CN.md)。本次仅整理文档，不重估预算或更新历史验收。


分析日期：2026-10-16。本文面向中国大陆首发并提供付费功能；是建议方案，不代表已部署或已达到所述指标。现场检查仅做只读访问，没有压测、修改数据或读取用户内容。

## 1. 已核实的起点

当前为 FastAPI、单个 Uvicorn 进程直接监听 HTTPS 443、SQLite WAL 和本机头像文件。服务器为 2 vCPU、约 1.9 GiB 内存、50 GB 磁盘；检查时磁盘已用约 5.8 GB、系统负载接近零。数据库约 68 KiB，仅有 4 个账号和 19 条房间登记。**空闲采样不能证明商业容量。** 音视频和房间消息主要经过腾讯云，不经过这台业务机转发。

发现 3 次同机历史备份，其中两份包含数据库与头像；未在 systemd timers、`/etc/cron.*`、`/var/spool/cron` 发现 Kiki 定时备份。没有检查云控制台，不能断言不存在云盘快照。实例、数据库、头像与这些备份仍共用故障域。

代码依据：[数据库与表](../../backend/app/main.py)、[单进程部署](../../backend/deploy/kikitalk.service)、[备份写锁](../../backend/deploy/backup.sh)。当前健康接口只检查数据库可读及配置存在，不代表云端通话、消息和支付全链路正常。

## 2. 生产数据域和核心表

保留独立业务 `user_id`，不把登录 ID、手机号、腾讯用户 ID 或设备 ID 作为主键。表均带创建时间；业务时间统一 UTC，金额使用整数最小单位，禁止浮点数。以下是逻辑表设计，实施时补充字段字典、迁移和数据分级。

| 数据域 | 核心表及关键约束 |
| --- | --- |
| 账户、身份与设备 | `users` 保存账户状态与注销状态；`identities(user_id,provider,subject)` 唯一 `(provider,subject)`；`provider_users(user_id,provider,app_id,external_user_id)` 唯一云身份组合；`devices`、`auth_sessions` 外键指向用户，token 仅存哈希，索引 `(user_id,revoked_at)`、`expires_at`。设备不等于用户，换机要经过身份验证。 |
| 房间与场次 | `rooms` 表示可复用业务空间；`room_sessions` 表示每次开播，包含房主、开始/结束、状态版本和云房间映射；外键指向用户、房间，云端映射按供应商和应用隔离。`room_participations` 记录进退场区间；`room_events` 记录已去重事件。索引 `(status,started_at,id)`、`(owner_id,started_at,id)`。麦位实时权威状态仍由指定引擎管理，不制造第二个独立写源。 |
| 订单与支付 | `products`、`orders`、`order_items` 固化成交价格、权益版本和币种；`payment_attempts` 支持重试；`payment_transactions` 唯一 `(channel,environment,external_transaction_id)`；`refunds` 唯一渠道退款号。订单外键不得级联删除交易，用户订单索引 `(user_id,created_at,id)`。 |
| 钱包与账本 | `ledger_accounts` 按主体、资产单位和用途区分；`ledger_transactions` 保存业务单号、幂等键和冲正关系；`ledger_entries` 外键指向事务、账户。唯一 `(business_type,business_id,posting_type)`；按 `(account_id,created_at,id)` 查询。人民币与虚拟币分别记账，不能混在一笔守恒式中。 |
| 会员与权益 | `subscriptions` 唯一渠道原始订阅标识；`subscription_events` 去重续订、退款、失效事件；`entitlements` 记录权益来源、有效期和版本。授权由服务端有效权益决定，不能相信本地购买成功提示。 |
| 安全与治理 | `reports`、`report_evidence`、`moderation_cases`、`sanctions`、`sanction_executions`、`appeals` 分离举报、证据、裁决、处罚和云侧执行。索引 `(status,priority,created_at)`、`(target_user_id,status,expires_at)`；处罚操作与管理员审计关联。 |
| 消息与 Push | `notifications`、`notification_deliveries`、`notification_preferences` 管业务通知；`push_registrations` 按平台、应用环境、设备保存加密 token 和有效状态，避免跨账号误投；失效回执撤销注册。私聊正文可由 IM 托管，业务库保存必要映射与举报证据，不盲目全量复制。 |
| 可靠事件 | `callback_inbox` 唯一 `(provider,event_id)`，无可靠事件号时使用经验证的规范化业务键；`outbox_events` 与业务写入同一事务，索引 `(status,next_attempt_at,id)`；消费者另设唯一去重键，保存重试、死信和人工补偿记录。 |

所有关联使用显式外键及受控删除策略。跨服务引用保留稳定 ID 与必要快照；对象存储的证据、头像必须有数据库元数据、状态和清理任务，不能只保存一个 URL。索引服务于实际查询，不给所有字段建索引；列表采用稳定游标分页。

## 3. 付费、账本与一致性边界

支付必须经过服务端向渠道验签、验单并核对商品、金额、币种、环境和订单归属，适配 Apple、安卓渠道及鸿蒙对应渠道。客户端成功回调只触发查询；渠道通知可能重复、乱序或晚到，退款和续订也要处理。保留原始业务凭据的受控证据及必要脱敏摘要。

账本采用追加复式或等价守恒设计：每笔事务在同一资产单位内借贷相等；可用、冻结、待结算、平台收入、主播应付分别建账户。扣款先锁定相关账户并检查可用余额，按固定顺序加锁；余额快照、分录、订单状态和 outbox 原子提交。数据库唯一约束解决并发重复，不能仅靠 Redis 锁。礼物发放、会员开通、退款、主播结算各有独立幂等业务键；同一幂等键对应不同请求内容必须报冲突。冲正追加反向分录，禁止修改或删除旧分录，定期与渠道、余额快照及主播结算对账。

账户注销仅清理或匿名化可删除的个人资料并撤销访问，**不能通过级联删除财务历史实现注销**。交易、必要审计和争议证据按经法务确认的分类期限受限保留；身份映射与财务主体关联最小化、加密并限制权限。备份恢复后也要重放注销与删除清单。

订单、余额、处罚、权益、账号状态及管理操作读写主库，支付后立即查询走主库。房间推荐、历史列表、统计可读副本，但明确允许延迟；读己之写通过主库路由或版本水位保障。Redis 只做缓存和短期状态，不能成为财务事实源。

## 4. 瓶颈与无状态改造

SQLite WAL 可并发读，但写入仍串行。当前登录在写事务中做 PBKDF2，头像写事务包含文件 `fsync`，备份持锁直到头像全部复制；数据增长会增加写排队。房间列表查询计划已出现全表扫描及临时排序，且接口固定最近 500 条。不能通过共享网络盘放 SQLite 来实现多机写。

迁移到托管 PostgreSQL 或 MySQL，建立版本化迁移、连接池和慢查询监控。头像转对象存储/CDN，上传审核使用隔离区和受控任务，避免大量图片解码占满 API 内存。API 无本地业务文件、会话和限流状态；限流迁 Redis，持久任务迁队列。负载均衡后至少两个 API 副本，独立 worker 处理审核、Push、回调和处罚；事务 outbox 弥补业务提交后发消息失败。

API 按延迟、CPU 和请求量扩容，worker 按队列等待时间及消费速度扩容。数据库先优化查询、索引、事务与规格，再考虑读副本；写主库扩容不是简单增加 API 副本。总连接池预算必须覆盖所有副本上限，预留管理和恢复连接。缩容要先摘流、排空请求和任务租约。首期保持模块化单体，达到实测边界再拆独立服务。

## 5. 容量模型与压测

以下仅为**演算假设**：峰值 10,000 在线用户，每 30 秒一次大厅请求，则约 `10,000÷30=333 RPS`；若每请求执行两次 SQL，粗略为 666 次查询/秒，仍需加入登录、进房、资料和后台任务。实际请求频率须从客户端埋点取得，不能直接用 DAU 推 RPS。

按平均响应 0.2 秒估算，`并发请求≈RPS×平均耗时`，333 RPS 对应约 67 个在途请求；这不是安全容量，尾延迟、突发和连接行为还会放大。当前 Uvicorn `limit-concurrency=100` 是 HTTP 并发限制，**不是只能支持 100 名在线用户**。

若每天 10 万张图片、平均 100 KiB，原始日增约 9.5 GiB，30 天约 286 GiB，尚未计版本、备份和 CDN 回源。媒体估算独立计算：在线参与分钟、音频/视频角色与码率、录制、审核、分发按实际云套餐核算，不能把所有腾讯云音视频带宽算到业务机。

压测需覆盖注册登录、读列表、并发进房、上传、支付通知重复乱序、处罚执行、队列故障与数据库恢复，使用脱敏数据和沙箱渠道，禁止直接对真实支付或生产媒体做破坏性压力测试。记录 p50/p95/p99、错误率、锁等待、连接池、内存、队列年龄及费用。

建议起始目标：关键业务月可用性 99.9%，普通 API p95 小于 500 ms，5xx 小于 0.1%；云依赖与自有服务分别观测。建议持续 5 分钟 CPU 超 60% 或延迟/队列越界触发扩容评估，持续 15 分钟低负载再缩容，并设最小副本、最大成本和人工接管。**这些均为待验证目标，不是已达成 SLO，也不是固定通用阈值。**

## 6. 备份恢复与分阶段验收

建议初始 RPO ≤15 分钟、RTO ≤60 分钟，由恢复演练验证。关系库使用自动全量加连续日志/PITR；对象存储启用版本、生命周期及跨故障域复制，关键备份放独立账号或不可变权限域。备份含 schema、对象清单、配置版本和受控密钥恢复材料，不能将密钥与备份公开打包。监控备份新鲜度、失败、复制延迟和恢复校验结果。

恢复流程：确认事故与恢复点 → 隔离新写入和受影响凭据 → 在独立环境恢复数据库与对应对象版本 → 校验账本守恒、订单/支付/权益、证据引用 → 对账并重放幂等回调、outbox、注销清单 → 验证身份、房间与支付查询 → 小流量切换并监控。不能从备份恢复后盲目再次扣款或发放权益。建议每季度及重大迁移前演练，记录实际 RPO/RTO。

1. **商用封闭测试前：** 固化数据字典、账号映射、处罚及支付状态机，补备份自动化和账本幂等测试；保留当前业务与 SDK ID。
2. **付费首发前：** 短维护窗口冻结 SQLite 写入，最终一致快照导入关系库，校验行数、外键、映射与对象哈希后切换；避免无保护双写。完成域名、对象存储、双 API 副本、队列和托管库。验收支付/退款/会员、举报封禁、重试去重及恢复演练。
3. **增长期：** 根据真实峰值压测建立扩缩容策略、读副本和分析管道。验收实例故障自动摘流、扩缩容不丢任务、恢复无重复交易，且峰值下仍满足确认后的 SLO 与成本预算。

每阶段须保留可回退版本和数据迁移说明。新结构产生写入后不能直接把流量切回旧 SQLite；回退需兼容同步方案或停写恢复计划。
